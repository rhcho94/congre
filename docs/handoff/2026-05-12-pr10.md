## 자체 학습

- "AI 자동 적용" 같은 요건은 일반 API 기능과 다른 영역. D 정찰 1차 라운드에서 transition·effect·filter는 봤지만 "자동 다양성"은 못 짚음. 운영자가 "Shotstack AI 자동"이라 말씀하셨을 때 별도 검색했어야. 다음부터 "자동"·"AI" 표현은 별도 정찰 항목으로 분리.

- 정찰 결과 사양이 깨지는 패턴 누적: 본 의제도 운영자 첫 사양 "자막 overlay로 인트로/아웃트로 전환" → 정찰 보고 받고 "호스트 미디어 + overlay 자막"으로 확장 → outroText 배치 한계 발견 → 운영자 판단으로 직렬 배치 수용. 정찰 1차에 모든 한계가 안 나옴. 정찰은 사양 확정의 끝이 아니라 시작점.

- Multi-track outroText 배치 정찰 결과 "기술적 한계로 새 길 없음" 결론에 도달. cont3 학습 "한 클로드는 자기 가설에 갇혀 있어 외부 검증이 효과적"과 다른 케이스 — 가설 문제 아니라 API 자체 한계. 다음부터 "이게 가설 한계인가 도구 한계인가" 구분하고 도구 한계면 운영자에게 솔직히 사양 재조정 카드 제시.

- 결정 사안이 13개 누적되는 과정에서 "한 번에 모호점 다 짚지 말고 가장 영향 큰 것 하나만 먼저" 학습을 부분적으로만 따름. 본 의제는 결정 사안이 서로 의존성 있어 묶이는 게 자연스러운 케이스였지만, 운영자 입장에서 질문 5~6개씩 누적은 부담. 다음부터 묶음 질문 시 "가장 영향 큰 둘만" 명시.

- 운영자가 outroText 배치 한계 보고 받고 "그건 실제적으로 전혀 문제 안 됨"으로 한 줄 정리하심. 채팅 클로드가 4가지 방안 + 추가 정찰 제안까지 갔으나 운영자 도메인 판단으로 즉시 종료. 기술 한계 보고 시 "실제 운영 영향"을 먼저 묻는 게 효율적이었을 것. 다음부터 기술 한계 보고 시 "이게 운영에서 어떤 시나리오로 발현되는가" 먼저 짚고 운영자 판단 받기.
