# 결제 도중 클립이 추가되는 경우 대응 — 콩그레 해결 정리 + 필드샷 적용 가이드

> 작성: 2026-09-21 (콩그레 세션 정리)
> 콩그레 기준 커밋: `9dd3a04` (main)
> 관련 결정: 콩그레 `docs/decisions/market-product.md` 2026-09-21 "결제 전 마감(`3615b9b`)을 되살리지 않는다"

---

## 0. 먼저 알아둘 것

- 이 문서의 코드 위치(파일:라인)는 **콩그레** 기준이다. 필드샷은 구조가 같다고 들었지만, **필드샷 코드는 본 적이 없다.** 파일명·필드명·상태값이 다를 수 있으니 반드시 정찰부터 한다(6장).
- 용어 풀이
  - **prepare** — 결제 준비 API. 결제 페이지에 들어올 때 그 순간의 클립 수로 금액을 계산하고 "주문서"(payments 문서)를 만든다. 가게로 치면 견적서 발행.
  - **confirm** — 결제 승인 API. 토스 결제창을 통과한 뒤 서버가 토스에 "이 결제 확정해 주세요"를 요청한다. 실제로 돈이 빠지는 건 이 순간.
  - **409** — HTTP 상태 코드. "요청 자체는 맞지만 지금 상태와 충돌한다"는 뜻. 여기서는 "견적서와 실제 클립 수가 다르다".

## 1. 문제 상황

유료 이벤트의 결제 흐름은 이렇다.

```
[마감하기] → 결제 페이지 (prepare: 이 순간 클립 N개로 주문·금액 생성)
          → 토스 결제창 (고객이 카드 정보 입력)
          → /payment/success (confirm: 토스에 최종 승인 요청)
```

**결제 페이지를 연 뒤 승인되기 전까지 참가자 업로드가 열려 있다.** 그 몇 분 사이에 클립이 올라오면, 주문서의 클립 수(N개)와 실제 클립 수(N+1개)가 달라진다. 금액이 틀린 채로 결제되거나, 결제한 적 없는 영상이 결과물에 들어가게 된다.

---

## 2. 콩그레의 원래 구조 (고치기 전)

**감지는 이미 있었다.** confirm이 토스에 승인을 요청하기 **전에** 클립 수를 다시 센다.

- 위치: `src/app/api/payment/confirm/route.ts:61-76` (최초 결제 모드에서만)
- 동작:
  1. 현재 포함 클립 수를 다시 센다 (`excludedAt`으로 제외된 것 빼고)
  2. 주문서의 `clipCount`와 다르면
     - 주문서를 `status: "stale"`(폐기)로 바꾸고
     - `409 { error: "CLIP_COUNT_CHANGED", savedCount, currentCount, newAmount }` 반환
  3. 토스 승인 호출보다 앞이라 **돈은 빠지지 않는다**
  4. 이벤트 문서는 건드리지 않는다 → 이벤트는 `open`(업로드 가능, 결제 전) 상태로 남는다

**문제는 출구였다.**

- 409 응답 본문에 `eventId`가 없었다.
- 성공 페이지(`src/app/payment/success/page.tsx`)는 eventId를 confirm 성공 응답에서만 받았다. 그래서 409 화면에서는 결제 페이지(`/payment/{eventId}`)로 보낼 수 없었다.
- 화면은 "대시보드에서 다시 결제를 진행해 주세요" + [대시보드로 이동] 링크 하나뿐이었다.
- 실제로는 대시보드 → 이벤트 열기 → [마감하기]를 다시 눌러야 결제창으로 갔다. "결제" 버튼을 찾는 고객이 헤맬 수 있었다.

### 3-3. 왜 이것만으로 재결제가 되는가

```
409 발생 → 주문서만 stale, 이벤트는 open 그대로
  → [새 금액으로 결제하기] → /payment/{eventId}
  → prepare 재호출: status "open" + 미결제 → "최초 결제"로 다시 받음
  → 클립 재집계 → 새 금액 계산 → 새 주문서 생성
      (orderId = `congre_${eventId}_${Date.now()}` 이라 옛 주문과 절대 안 겹침)
  → 토스 결제창 → confirm → 이번엔 수가 같으니 승인
```

409 화면이 안내한 `newAmount`와 새 결제 페이지 금액은 같은 계산식(`calcPrice(maxClipSeconds, clipCount)`)이라 일치한다.

## 4. 적용 전 반드시 확인한 안전 조건 3가지

필드샷에도 **똑같이** 확인해야 한다.

| # | 확인 | 콩그레 결과 | 왜 중요한가 |
|---|---|---|---|
| 1 | 409가 **로그인 확인 + 주문 소유 확인 이후**에 나가는가 | 예. `verifyIdToken`(`:10-13`) → `order.hostId !== uid` 403(`:33-35`) → 409(`:65-76`) 순서 | 순서가 거꾸로면 409 응답에 실은 eventId가 남에게 샌다 |
| 2 | 409 시점에 이벤트가 **결제 가능한 상태로 남는가** | 예. confirm이 이벤트 문서를 쓰는 곳은 승인 성공 이후뿐 | 이벤트가 바뀌면 prepare가 "최초 결제"로 안 받아줘서 버튼이 막다른 길이 된다 |
| 3 | 재사용한 `eventId` 상태에 **부수 동작이 없는가** | 없음. 읽는 곳 5곳 전부 화면 렌더 안, `useEffect` 의존성에 없음 | "eventId가 채워지면 자동 이동" 같은 코드가 있으면 409 화면에서 엉뚱하게 튄다 |

## 5. 선택하지 않은 방법: 결제 전 마감

**방법:** 결제 페이지로 가기 **전에** 이벤트를 마감(업로드 차단)한다. 결제 중 클립 추가 자체가 불가능해진다. 콩그레에서 한 번 구현(`3615b9b`)했다가 롤백했다.

**콩그레가 되살리지 않은 이유:**

1. "마감했지만 결제 안 한" 상태가 새로 생긴다. 상태값(`status`)을 읽는 30곳 이상을 다시 점검해야 한다.
2. 마감 후 결제를 안 하고 방치하면, 정리 작업(cleanup)이 마감 시각 기준 7일 뒤 클립을 지운다.
3. 실제로 한 번 유료 결제를 막았다. prepare의 최초 결제 조건이 `status === "open"`인데, 마감을 앞당겨 스스로를 막았다.

**현행으로 충분하다고 본 근거:** confirm이 승인 성공 순간 이벤트를 마감한다. 남는 틈은 결제 중 몇 분이고, 그 사이 수가 바뀌면 409가 잡는다.

**감수한 위험:** 그 몇 분 사이에 **개수는 같게** 바뀌면(예: 1개 제외 + 1개 업로드) 409에 안 걸린다. confirm은 개수만 비교하기 때문이다.

**재검토 트리거:** "확인하지 않은 영상이 완성본에 섞였다"는 문의·분쟁이 생길 때.

→ 필드샷도 같은 판단을 따를지는 **Ray가 결정**. 필드샷 코드 정찰 후 상태값 구조가 다르면 판단이 달라질 수 있다.

## 6. 필드샷 적용 절차

**정찰 → 결정 → 실행 → 검증** 순서. 확인 단계와 실행 단계를 한 프롬프트에 합치지 않는다.

### 6-1. 정찰 프롬프트 (확인 전용)

```
[커밋 금지 — 확인만. 코드 수정 금지. git stash 금지. 현재 브랜치 유지]

결제 도중 클립 수가 바뀌는 경우의 처리를 정찰해줘. 해법 제안 없이 사실만.

1. 결제 흐름 지도: 결제 준비(prepare 류) → 토스 결제 → 결제 승인(confirm 류) → 성공 페이지.
   각 단계의 파일:라인. 성공 페이지로 이동시키는 코드 전부(successUrl 포함).
2. 결제 준비 API가 주문서에 클립 수를 저장하는지. 저장한다면 필드명과 위치.
3. 결제 승인 API가 토스 승인 요청 "전에" 클립 수를 다시 세서 주문서와 비교하는지.
   - 비교한다면: 다를 때의 처리(주문 상태 변경, 응답 코드, 응답 본문 필드 원문).
   - 비교하지 않는다면: "없음"이라고 명시.
4. 그 불일치 응답이 인증(idToken 검증) + 주문 소유 확인 "이후"에 나가는지. 가드 순서를 파일:라인으로.
5. 불일치 시점에 이벤트 문서가 바뀌는지. 바뀌지 않는다면 결제 준비 API가 같은 이벤트를
   다시 최초 결제로 받아주는지(분기 조건 원문).
6. 성공 페이지가 불일치 응답을 받았을 때의 화면·링크. eventId(또는 해당 식별자)를
   어디서 얻는지, 불일치 응답에서도 얻을 수 있는지.
7. 성공 페이지의 eventId 상태를 읽는 곳 전부, useEffect 의존성에 들어가는지.
8. 현재 브랜치명과 최근 커밋 5개(git log --oneline -5).

보고: 백틱 4개 코드 블록 하나에. 주장마다 파일:라인, 직접 확인 / 추론 구분, 확인 못 한 것은 "확인 못 함".
합계 표·요약 표 붙이지 마.
```

### 6-2. 정찰 결과에 따른 갈래

| 정찰 결과 | 할 일 |
|---|---|
| **감지 있음 + 출구 없음** (콩그레와 같은 상태) | 3장과 동일하게 수정 (6-3) |
| **감지 자체가 없음** (승인 API가 클립 수를 다시 안 셈) | 먼저 감지 추가가 필요하다. 토스 승인 호출 **전에** 재집계 → 다르면 주문 폐기 + 409. 이건 돈이 걸린 로직이라 **별도 설계 논의 후 별도 커밋**. 그 뒤 출구 수정 |
| **감지 있음 + 출구도 있음** | 할 일 없음. 4장 안전 조건만 확인 |
| **이벤트 상태 구조가 다름** (예: 불일치 시 이벤트가 바뀜) | 3-3의 "재결제가 되는 이유"가 성립 안 할 수 있다. 수정 전에 설계 논의 |

### 6-3. 실행 프롬프트 템플릿 (감지 있음 + 출구 없음일 때)

> 파일 경로·필드명은 정찰 결과로 바꿔 넣는다.

```
[커밋 금지 — 코드 수정 후 빌드 확인 + diff 보고까지만. git stash 금지. 브랜치 이동 금지]

결제 도중 클립 수가 바뀌어 409가 났을 때, 성공 페이지에서 결제 페이지로 바로 갈 수 있게 한다.

사전 확인 (조건이 안 맞으면 수정하지 말고 멈춰서 보고):
- 409 반환이 인증 + 주문 소유 확인 이후에 실행되는지.
- 409 시점에 이벤트가 결제 가능 상태로 남는지.

변경 1 — <결제 승인 API 파일>
- 409 응답 본문에 eventId 추가. 기존 필드는 그대로. 이미 스코프에 있는 주문서의 eventId 를 쓸 것.

변경 2 — <성공 페이지 파일>
- 409 분기에서 응답의 eventId 를 상태에 저장.
- 409 화면: 주 버튼 [새 금액으로 결제하기] → /payment/{eventId}, 보조 링크 [대시보드로 이동].
  eventId 가 없으면 대시보드 링크만.
- "대시보드에서 다시 결제" 식 문구는 버튼 기준으로 수정. 바꾼 문구 원문 보고.
- 버튼 스타일은 같은 파일의 다른 화면 클래스를 따를 것.

금지: 위 2개 파일 외 수정 금지. 409 외 분기 변경 금지.

확인:
1. 빌드 통과.
2. lint 전체 delta + 2개 파일 단독 결과.
3. 흐름 설명: 409 → 버튼 → 결제 준비 API가 최초 결제로 새 주문·새 금액을 만드는 경로 (파일:라인).
4. 성공 페이지 eventId 상태를 읽는 곳 전부와 useEffect 의존성 여부.

보고: 백틱 4개 코드 블록 하나에. git diff 원문(요약·헤더 편집 금지), 라인 수 직접 집계 + --numstat 병기.
```

diff 검증 후 커밋은 **별도 프롬프트**(`[커밋 허용 — 커밋 + push]`)로 한다.

### 6-4. 실화면 검증 (테스트 키, 기기 2대)

```
준비: 유료 이벤트, 영상 1개 이상 업로드, 미결제

[PC]  [마감하기] → 결제 페이지 열림 (여기서 멈춤)
[폰]  참가자 업로드 링크로 영상 1개 추가
[PC]  결제하기 → 테스트 결제
      기대: "결제 준비 시점 N개 → 현재 N+1개…" + [새 금액으로 결제하기]
[PC]  [새 금액으로 결제하기]
      기대: N+1개 기준 결제 페이지
      (끝까지 가려면 결제 → 렌더 → 완성까지 확인)
```

- 최소 결제 금액이 있으면 영상 1개가 늘어도 **금액은 안 바뀔 수 있다.** 판정 기준은 금액이 아니라 **개수 변화**라 409는 그대로 나야 한다.
- 결제창에서 카드사를 안 고르면 "결제 요청 중 오류" 팝업이 뜬다. 입력 누락이지 이 기능의 문제가 아니다.

## 7. 같은 결제 구조라면 함께 점검 권장

콩그레에서 같은 날 처리한 것들이다. 필드샷에도 같은 구멍이 있을 수 있다.

| 항목 | 콩그레 처리 | 필드샷 정찰 포인트 |
|---|---|---|

## 8. CC 작업 원칙 (콩그레에서 겪은 것)

- **프롬프트 첫 줄에 "커밋 허용 / 커밋 금지"를 반드시 적는다.** 훅이 커밋·push를 요구해서, 프롬프트가 침묵하면 CC가 검토 전에 커밋한다.
- **미커밋 상태의 확인 작업에서 `git stash` 금지.**
- **작업 브랜치를 확인한다.** CC가 옛 브랜치를 "지정 브랜치"로 착각한 적이 있다.
- **diff는 원문으로 받는다.** 요약·헤더 편집된 diff를 원문처럼 보고한 적이 있다.
- 증상 판단은 **로그의 Path 필드부터** 본다. 기억 속 증상보다 로그가 우선이다.
