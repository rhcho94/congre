#### 게스트 도달 패턴 결정 — 진화 과정

운영자 한 마디로 가정 깨지면서 추천안이 두 번 뒤집혔다. 그 흐름과 학습 정리:

1. **초기 추천 — 패턴 A (호스트가 기존 단톡방에 share 링크)**: 1순위 시장(졸업식)에 학급 단톡방이 자연스럽게 있다는 가정. 운영자가 "단톡방 자체가 부담스러울 수 있고, 게스트들끼리 서로 모를 가능성 높다"로 가정 깸.
2. **2차 추천 — 패턴 B (SMS 자동 발송)**: 게스트 이름 + 전번 사양으로 변경 (evening 핸드오프 결정 항목과 정합), 렌더 완료 시 SOLAPI로 자동 발송.
3. **운영자 추가 사양 — 두 채널 병행**: B만이 아니라 A도 함께. 자동 SMS는 영상 올린 게스트에게만, 호스트 카톡 공유는 누구에게나(가족·친구·구경꾼 포함).

#### 1단계 / 2단계 분리 결정

두 채널 병행 사양 확정 후, **1단계(share 페이지) + 2단계(게스트 사양 변경 + 호스트 발송 UI + SMS 트리거 연결)** 두 세션으로 분리. 근거:
- 1단계는 파일 2개 변경, 2단계는 파일 10개 이상 변경 (사실상 3~4 PR 규모)
- share 페이지가 안정돼야 SMS 본문에 들어갈 URL이 검증된 상태가 됨 (의존성)
- 게스트 사양 변경은 며칠 전 닉네임 작업 자리 다시 건드림 — 추가 결정 필요 (전번 검증 형식·중복 정책·sessionStorage·기존 닉네임 컬럼 마이그레이션 등)

**첫 회차 필드 테스트는 1단계 + 2단계 모두 완료 후 진입**으로 결정.

#### 카카오 SDK 제약 명확화 (학습용 보존)

운영자 질문 중 두 가지가 카카오 정책 제약에 걸렸다. 다음 세션에서 사양 결정 시 재참조:
- "카톡 공유 시 게스트들 자동 선택 후 발송 가능?" → **불가**. 카카오 공유 시트는 사용자가 수신자 직접 고르는 UI. 외부에서 미리 선택 못 시킴.

**증상**: PC 크롬에서 `/share/{eventId}` 진입 시 500. 카톡 카드 클릭 시 "This page couldn't load, ERROR 3602376030" (digest 일치).

**진단 흐름**:
1. 첫 가설: Vercel 환경변수 / Edge Runtime 충돌 / 데이터 형태 불일치 (셋 다 빗나감)
2. Vercel Logs Live 모드 + PC 크롬 직접 진입으로 사고 재현
3. 에러 본문 확보: `Firestore has already been initialized. You can only call settings() once`
4. CC 정찰: `src/lib/firebase-admin.ts`의 `_db` 모듈-레벨 가드가 SSR 모듈 격리 환경에서 안 통함. share 페이지의 generateMetadata + SharePage 두 함수가 별도 모듈 인스턴스에서 각각 `getAdminDb()` 호출 → 같은 firebase-admin 내부 Firestore 객체에 `.settings()` 두 번 → throw.
5. 수정: `_db.settings()` 호출을 try/catch로 감싸고 "already" 에러만 무시, 그 외 re-throw.
6. 검증 통과 (`eb68955`).

**known-issues.md 등록 완료**: `## ✅ SSR 서버 컴포넌트 getAdminDb() 중복 호출 — settings() throw [RESOLVED 2026-05-09]`

### 자체 학습 (이번 세션)

#### 분석·추론 패턴

- **빌드 통과 ≠ 런타임 동작 보장**: 새 진입점이 SSR + admin SDK 호출 같은 새 패턴인 경우, push 전에 운영자 로컬 dev에서 한 번 진입 확인하는 단계가 정합. 이번엔 푸시 직후 카톡으로 사용자가 첫 진입했고 사고가 거기서 발화. CC 작업 직후 → push 전에 운영자 로컬 npm run dev로 한 번 진입 확인 → 통과하면 push로 워크플로 보강 검토 가치 있음.
- **SSR 모듈 격리로 모듈-레벨 싱글톤 깨짐**: `let _db: Firestore | null = null` 같은 모듈-레벨 가드는 SSR 서버 컴포넌트의 generateMetadata + 페이지 함수 사이에서 안 통함. 두 함수가 별도 모듈 인스턴스에서 실행되면 가드가 분리됨. 미래에 비슷한 모듈-레벨 싱글톤이 코드베이스에 추가되면 같은 사고 가능 — 지금 grep 점검은 YAGNI, 알려진 이슈로만 등록.
- **1순위 시장의 시장 특성 → 사양 자동 추론 금지**: "1순위 시장이 졸업식이니 학급 단톡방 자연스럽다"는 추론이 한 단계 너무 빨랐다. 졸업식이라도 콘텐츠 사양("본인 1인칭 소감")에 따라 게스트 풀이 학급 전체가 아니라 호스트가 개별 초대한 사람들일 수 있고, 서로 모를 가능성 높음. 시장 정의에서 사양 직결 추론은 운영자 검증 필수.
- **로그 없음 = 코드 문제 자동 추정 금지**: 진단 단계에서 "Vercel 로그에 share 요청이 안 보임"을 코드 문제 신호로 처음 해석. 실제로는 시간 범위 + production 도메인 매핑 문제. **요청이 어디까지 도달했는지부터 확인**하는 패턴이 정합. 갈래: (1) Vercel Edge Network까지 도달했나, (2) Function 호출됐나, (3) Function이 throw했나 — 단계 분리 진단.
- **Vercel UI 정보 위계 ≠ production 매핑**: 배포 목록 위계와 production 도메인 매핑이 항상 일치하지 않음. "어느 배포에 `congre-three.vercel.app` 도메인이 붙어 있는가"를 우선 확인하는 패턴이 정합.

#### 운영 패턴

- **결정 단계에서 사용자 한 마디로 가정 깨지는 흐름은 정상**: 추천안이 두 번 뒤집힌 건 운영자 직관이 추천안 구멍을 메운 사례. 자책 사례 아님. 다음 세션 SMS 사양 짤 때도 같은 검증 패턴(추천 → 운영자 가정 깨기 → 사양 정합화)으로 가는 게 정합.
- **AI 도구 자체 정보는 검색 우선**: 로고 만들 때 학습 데이터 시점 이후 신규 서비스·가격 정책이 바뀌었을 가능성 큼. AI 로고 도구 추천 같은 영역은 검색 한 번 거치는 게 정합.

## 자체 학습 (다음 세션 클로드용)

### 분석·추론 패턴
- **시장별 분기 자동 추정 금지**: 사양 결정 시 "시장별로 다를 수 있다"는 답을 자동으로 내지 말기. 통일 사양 vs 분기 사양은 운영자 결정 영역.
- **외부 콘솔 메뉴 트리는 추정 안내 금지**: 카카오·Firebase 등 외부 콘솔 메뉴 경로 안내 시, 운영자 화면 캡처 먼저 받은 후 안내. 추정으로 메뉴 트리 제시 X.
- **dead code = 기능 미구현 등식 주의**: DECISIONS에 "구현 예정"이라 적혀 있어도 실제 호출 코드가 없으면 미구현. 두 단계 검증 (문서 확인 → 코드 grep).
- **비용 비교표에서 0원 항목 명시**: egress $0 같은 항목은 "0" 또는 "$0/GB"로 명시. 빈칸 두지 말기.
- **임시 회피 vs 본질 해결 갈림길에서 도메인 제약 먼저**: "이게 동작 안 하면 데이터 자체가 의미 없는가"를 먼저 확인. 이 질문에 "그렇다"이면 임시 회피 기각.
- **사양 항목 간 의존성 명시**: 결정 항목 작성 시 "이 결정은 저 결정에 의존"을 함께 적기.

### 운영 패턴
- **세션 길어지면 능동적 매듭 제안**: 컨텍스트가 길어지고 결정이 쌓이면 "여기서 핸드오프 작성 후 다음 세션에서 작업할까요?" 능동 제안. 운영자가 매번 짚게 두지 말기.
