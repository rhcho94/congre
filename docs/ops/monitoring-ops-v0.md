# Congre 운영 점검 문서 (v0) — 수동 모니터링 + 한도·비용

> 모니터링 화면을 만들기 전, 정찰로 얻은 정보를 한 곳에 모아 두고 이 문서로 직접 확인한다.
> 화면 빌드는 나중. 지금은 이 문서가 (1) 임시 모니터링 매뉴얼, (2) 정찰로 채울 양식 두 역할.

---

## 0. 이 문서 사용법

- **표시 규칙**
  - 🟦 = **CC 정찰**(코드)로 채울 칸. CC 프롬프트 → 보고 → 채팅 클로드 검증 후 기입.
  - 🟨 = **운영자**가 각 서비스 대시보드에 로그인해 채울 칸. (채팅 클로드는 이 칸 못 봄)
  - ⬛ = 이미 채워진 칸(채팅 클로드가 docs 기준으로 기입). 추정은 "추정"이라고 적음.
- 빈칸(`____`)을 채우는 것 = "확인 완료". 채우면서 이상하면 메모를 옆에 단다.
- 수치 중 "추정 / 확인 필요"는 그대로 두지 말고, 정찰·대시보드에서 실제 값으로 교체한다.

## 1. 수동 모니터링 — 호스트/이벤트 현황 보기

> 데이터는 전부 **Firestore**(구글 데이터 저장소, 엑셀 파일 묶음 같은 것)에 있다.
> 화면이 없으니 당분간은 Firebase 콘솔에서 직접 들여다본다.

### 1-1. Firebase 콘솔 접근 경로 (🟨 운영자가 실제 메뉴와 대조)

```
console.firebase.google.com 로그인
└─ 프로젝트 congre-mvp 선택
   └─ 좌측 메뉴 "Firestore Database" (또는 "빌드 > Firestore Database")
      └─ "데이터" 탭에서 컬렉션 목록(users / events / clips / notifications) 클릭
```

- 실제 메뉴 이름이 위와 다르면 → 추측으로 헤매지 말고 첫 화면 캡처해서 채팅 클로드에 전달.

### 1-2. 무엇을 보나 (컬렉션별 의미) ⬛

| 컬렉션 | 들어있는 것 | 확인용 |
|---|---|---|
| `users` | 가입한 호스트 | 누가/언제 가입했나, 이메일 인증했나 |
| `events` | 만들어진 이벤트 | 이벤트 상태, 영상 완성 여부 |
| `clips` | 참가자가 올린 영상 조각 | 이벤트별 참여 수 |
| `notifications` | 발송된 알림 이력 | (Admin 전용, 콘솔에서 열람만) |

### 1-3. 데이터 모델 참고표 — "콘솔에서 무슨 글자를 보게 되나"

> 콘솔은 필드 이름 그대로 보여주므로, 아래 표가 있어야 운영자가 화면을 해석할 수 있다.
> 🟦 CC 정찰 B 결과로 확정 교체. 아래는 docs 기준 **추정** — 그대로 믿지 말 것.

**users 문서 필드** 🟦
- 추정: `name`, `phone`, 이메일 인증 여부 필드(`email_verified` 추정), 가입일(`createdAt` 추정)
- 실제 필드 목록: `________________` (CC가 채움)

**events 문서 필드** 🟦
- 추정: `hostId`(또는 소유자 식별 필드), `status`, `videoUrl`, 인트로/아웃트로 텍스트, `clipsDeletedAt`, `videoDeletedAt`
- 실제 필드 목록: `________________` (CC가 채움)

**clips 문서 필드** 🟦
- 추정: `eventId`, `uploaderName`, `uploaderPhone`, 업로드 시각
- 실제 필드 목록: `________________` (CC가 채움)

**events.status 가질 수 있는 값 + 뜻** 🟦
- 추정: `standby`(모집 중) / `closed`(마감) / `rendering`(편집 중) / `done`(완성)
- 실제 값 전체: `________________` (CC가 채움)

> ※ 이 표가 채워지면, "콘솔에서 events 열어 status가 rendering인데 한참째다 → 렌더 지연 의심" 같은 판단이 가능해진다.

### 2-2. 조용히 실패하는 것 — 특별 주의 ⬛

에러도 안 뜨고 그냥 안 되는 것들. 제일 위험하다.
- **SOLAPI 잔액 소진** → SMS 발송 실패하는데 화면엔 아무 표시 없음.
- **메일 일/월 한도(Resend·Firebase)** → 인증/알림 메일 미발송.
- → 이 영역은 향후 **C(운영자 알림)**가 잡아줄 부분과 겹침. 렌더 실패/지연을 운영자가 푸시로 받으면 시야에 들어온다.

## 3. 운영자 정기 점검 루틴 (화면 생기기 전 임시)

> 화면이 없으니 손으로 본다. 빈도는 운영 상황 보며 조정.

- **수시 / 새 이벤트 알림 받을 때**
  - [ ] Firebase 콘솔 `users` — 신규 가입자 수, 인증 안 한 계정 있나
  - [ ] Firebase 콘솔 `events` — status가 `rendering`에서 오래 멈춘 게 있나(렌더 지연 의심)
- **주 1회**
  - [ ] AWS Billing — 이번 달 비용 추세
  - [ ] SOLAPI 잔액 — 바닥 가까우면 충전
  - [ ] Shotstack usage — 렌더/전송량
- **사고 신호 감지 시**
  - [ ] "메일 안 와요" 다수 → Resend/Firebase 메일 한도 (known-issues 네이버 도달성 항목도 참조)
  - [ ] "가입이 안 돼요" → 이메일 인증 한도 또는 Firestore 한도

## 4. 출시 전 차단 항목 (must-do 체크리스트)

> 이게 안 되어 있으면 출시 첫날 사용자가 막힌다. 비용형은 "터지기 전 알림"이 전부.

- [ ] **AWS Budgets 비용 알림** 설정 (월 한도 정해 메일 받기) — 비용 1순위 🟨
- [ ] **Firebase 예산 알림** 설정 (Blaze일 경우) 🟨
- [ ] **Vercel 본앱 = Pro 여부 확인** (상업 출시면 Pro가 사실상 필수) 🟨
- [ ] **SOLAPI 잔액** 충분히 충전 🟨
- [ ] **Firestore composite index** 미리 생성 (clips: eventId+uploaderPhone+uploaderName) — 안 하면 첫 업로드부터 거부 (known-issues 기재) 🟦/🟨
- [ ] **렌더 지연 감지 cron**이 실제로 도는지 (GitHub Actions throttling 이슈) 🟦
- [ ] (플랜 결정) 무료 한도 cliff는 우회 말고 유료가 표준. 어느 걸 언제 올릴지는 운영자 결정.

## 5. 앞으로 (메모)

- **모니터링 화면(/admin 류)** — 호스트 수 수십 명+ / 영업 본격화 시점에 빌드. 그때 events read 차단 때문에 서버 라우트(Admin SDK) 경유 필요.
