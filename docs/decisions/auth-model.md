# Decisions — Auth Model

> 호스트 인증·이벤트-바운드 모델 관련 결정. 새 결정은 맨 위에 추가 (최신이 위).

## 2026-05-21 — 회원 탈퇴 차단 범위 축소 — closed 제외

- **결정**: 진행 중 이벤트 차단 조건을 `["open", "closed", "rendering"]`에서 `["open", "rendering"]`으로 축소.
- **배경**: 클립 0개로 마감(close)한 이벤트는 rendering으로 전이 불가. closed 상태로 영구 정체 → 호스트 탈퇴 불가 데드락 발생.
- **트레이드오프**: 마감만 하고 렌더 미시작한 closed 이벤트도 탈퇴 시 일괄 삭제됨. confirm 다이얼로그 본문 "모든 이벤트가 즉시 삭제"에 포함됨.
- **Race 평가**: closed → rendering 자동 전이 경로 없음 (정찰 A 확인). 사용자가 탈퇴와 렌더 시작을 동시에 호출할 확률 무시 가능.
- **변경 파일**: `src/app/api/user/delete/route.ts`, `src/app/mypage/page.tsx` 각 1라인.

## 2026-05-19 v3 — 이메일 인증 차단 흐름 (P3) + Custom Action URL + congre.kr 발신 도메인

- **결정**: 미인증 호스트에 대한 이메일 인증 차단 흐름 3개 레이어 구현.
  1. Firestore 보안 규칙: events create에 `request.auth.token.email_verified == true` 조건 추가. 콘솔 게시 완료 (2026-05-19 v3).
  2. 대시보드 UI: 미인증 시 "새 이벤트" 버튼 비활성 + "이메일 인증 후 이용 가능" 라벨 + `EmailVerificationBanner` (재발송 60s 쿨다운 + 인증 완료 확인 버튼).
  3. `/dashboard/create` 가드: 미인증 접근 시 `/dashboard` 리디렉션.
- **P3b 추가**: Custom Action URL (`/verify-email`) + `applyActionCode` 처리 페이지. `useRef` 이중 실행 가드 (React Strict Mode 대응).
- **P3d 추가**: `congre.kr` 이메일 발신 도메인 커스텀 설정. DNS 4개 레코드 (TXT SPF, TXT verification, CNAME DKIM ×2). Firebase Console Templates Action URL: `https://app.congre.kr/verify-email`. DNS 검증 완료: 2026-05-19 v3. Gmail 발신 도달 실측 확인 (2026-05-20).
- **YAGNI 결정**: `actionCodeSettings` 공용화 안 함 (사용처 2곳 — `auth.ts` + `EmailVerificationBanner.tsx`. 3곳 이상 시 격상).
- **이유**:
  - Firestore 규칙 단독으론 사용자 피드백 없음 → UI 레이어 병행.
  - 미인증 호스트 이벤트 생성 차단은 결제 연동 시 신뢰 이메일 보장 전제.
  - Custom Action URL 없으면 Firebase 기본 도메인 `/action?oobCode=...` 랜딩 → 앱 내 처리 불가.
- **관련 커밋**: `bada6d0` (P3a), `08be31f` (P3b).

## 2026-05-19 v2 — 호스트 가입 페이지 + users 컬렉션 채택, 5/9 보류 정정

- **결정**: 같은 영역에서 2026-05-09에 두 번 등록된 결정(첫째: 가입/로그인 페이지 분리, 둘째: 이벤트-바운드 모델)과 셋째 보류 결정을 사실상 정정. **계정 모델로 진입 — `/signup` 가입 페이지 + `users/{uid}` 컬렉션 + 이메일 인증 발송**.
- **결정 배경**:
  - 2026-05-18 v2 세션에서 영업 개시까지 출시 로드맵(`docs/launch-roadmap.md`) 정리. S2-03 호스트 가입 정비를 STAGE 2 진입점으로 확정. 5/9 보류 결정이 사실상 무효화됐으나 auth-model.md에 미반영 상태였음.
  - 2026-05-19 v2 세션에서 채팅 클로드가 외부 자료 조사(Firebase Auth 공식 가이드 + SaaS 사례) 후 사양 정정 → P1·P2 구현.
- **현재 적용 사양**:
  - 가입 페이지: `/signup` (별도 라우트). 기존 `/host` 단일 파일에 4번째 뷰 추가 대신 별도 페이지 분리.
  - 가입 처리: 클라이언트 SDK 직접 (`createUserWithEmailAndPassword` + `sendEmailVerification` + `setDoc(users/{uid})`). Admin SDK 경유 API 라우트 안 만듦.
  - users 컬렉션: `email` (lowercase), `name`, `phone` (10~11자리 숫자), `createdAt`, `termsAgreedAt`, `privacyAgreedAt`. doc ID = Firebase Auth UID.
  - emailVerified 필드: users 컬렉션에 저장 안 함. 보안 규칙에서 `request.auth.token.email_verified` 직접 활용 가능.
  - 고아 계정 처리: setDoc 실패 시 `createdUser.delete()` rollback.
  - 가입 직후 동선: `/dashboard` 직행. 이메일 미인증 차단 흐름: **2026-05-19 v3 P3 완료** (아래 v3 결정 참조).
  - 토큰 전파: 가입 직후 `getIdToken(true)` 호출 (외부 자료 표준 edge case 예방).
- **이유**:
  - 외부 자료 조사 결과 Admin SDK 가입은 invite·도메인 검증 같은 특수 케이스용. 일반 가입은 클라이언트 SDK 직접이 표준.
  - emailVerified를 Firestore에 중복 저장하면 Cloud Function 동기화 필요 → 운영 부담 ↑. Auth 진실값 직접 활용이 단순.
  - 이벤트-바운드 모델(5/9 둘째 결정)은 영속 호스트 계정 없는 흐름이라 마이페이지·결제 이력·다회 사용 지원 어려움. 영업 개시 후 한 계정으로 다회 이벤트 + 결제 + 환불 모델 정합 위해 계정 모델 채택.
- **트레이드오프**:
  - 미성년자 데이터 영속 보유 영역 — 호스트는 교사·학교 직원 등 성인 가정. 미성년자(학생) 데이터는 events·clips 내부에만, users 컬렉션엔 없음.
  - 가입 페이지 작업 사이즈 영역 — 4단계(P0~P3 통합) 완료.
- **본 세션 사고 패턴 학습 (2026-05-19 v2 핸드오프 Track E 참조)**:
  - 외부 자료 가설(토큰 timing)이 결정타 아닌 사례 → 표준 가설 채택해도 실측 검증 우선.
  - Firestore 규칙 git push만으로 미반영 → CLAUDE.md 신규 룰 등재.
  - catch 블록 console.error 누락 → CLAUDE.md 신규 룰 등재 (Shotstack 룰과 일관성).
- **관련 결정 폐기 / 정정**:
  - 2026-05-09 첫째 결정 (가입/로그인 페이지 분리) — 본 결정으로 부활 (가입 페이지 신설).
  - 2026-05-09 둘째 결정 (이벤트-바운드 모델 채택) — 본 결정으로 **정정**. 계정 모델로 회귀.
  - 2026-05-09 셋째 결정 (옵션 A 콘솔 수동 생성 + 인증 모델 보류) — 본 결정으로 **보류 해제**.

## 2026-05-09 — 호스트 계정 운영 방식 (옵션 A) + 인증 모델 결정 보류

- **결정**: 필드 테스트 단계의 호스트 계정 운영 방식을 옵션 A(Firebase 콘솔 수동 생성)로 확정. 인증 모델 자체의 결정(계정 모델 vs 이벤트-바운드)은 필드 테스트 첫 회차 결과를 본 후 재결정으로 보류.
- **이벤트-바운드 모델 채택 결정도 보류 처리**: 영향 범위가 갈래 1A~1G 7개 갈래 규모로 큰 작업이며, 필드 테스트 첫 회차 결과 보고 모델 자체에 대한 새 발견이 나올 수 있음. 모델 작업을 시작하기 전 진짜 사용 패턴 데이터 확보가 정합.
- **옵션 A 운영 절차**:
  - 필드 테스트 호스트마다 운영자가 Firebase 콘솔에서 사용자 추가 (Authentication → Users → Add user)
  - 이메일 + 임시 비번을 카톡/문자로 호스트에게 전달
  - 호스트는 /host에서 로그인 (현재 코드 그대로 동작)
  - 사용자가 비번 분실 시 기존 비번 재설정 모달로 자가 복구
  - 필드 테스트 종료 후 콘솔에서 계정 일괄 삭제 + 해당 hostId의 events 정리
- **이유**:
  - 코드 변경 0. 모델 결정과 완전 독립.
  - 운영자가 자기 계정 만들 때 한 번 해본 흐름 재사용.
  - 필드 테스트 N명 규모(10~30명 × 2~3회)에서 호스트는 회당 1~2명, 총 5~10명 콘솔 작업 — 1인당 30초로 부담 작음.
  - 모델 결정을 첫 회차 후로 미뤄서 작업 두 번 막음.
- **트레이드오프**: 운영자 수동 부담 + 비번을 운영자가 알게 됨. 1차 단계 임시 운영이라 수용 가능.
- **재결정 시점**: 필드 테스트 첫 회차 종료 후 인터뷰에서 모델 결정.
- **대안**: 가입 페이지 신설 (이벤트-바운드 전환 포함) — 7개 갈래 규모, 필드 테스트 데이터 없이 진행하는 비용 큼 → 보류.
- **2026-05-19 정정**: 본 결정의 보류는 2026-05-19 결정으로 해제됨. launch-roadmap 영업 개시 의제가 필드 테스트 결과보다 앞섰음.

## 2026-05-09 — 호스트 인증 결정 폐기 + 이벤트-바운드 모델 채택

- **결정**: 같은 날(2026-05-09) 등록된 "호스트 인증: 가입/로그인 페이지 분리" 결정을 폐기. 대신 이벤트-바운드 모델로 전환.
- **이벤트-바운드 모델**:
  - 가입 개념 없음. hosts 컬렉션 만들지 않음. 영속 호스트 계정 없음.
  - 이벤트 생성 폼에 이메일/이름/휴대폰번호/약관동의 입력. 비밀번호 없음.
  - 서버가 이벤트 생성 시 hostToken 발급. `events/{eventId}.hostToken` 필드에 저장.
  - 호스트에게 이메일+SMS로 관리 링크 발송 (예: `/dashboard/events/{eventId}?hostToken=...`).
  - 호스트는 그 링크로 이벤트 관리 진입. 토큰 분실 시 "이메일로 관리 링크 다시 받기" 흐름으로 복구.
  - 이벤트 + 호스트 정보가 한 묶음. 이벤트 삭제 = 호스트 정보 삭제. 데이터 보유 기간이 이벤트 수명과 동일.
- **이유**:
  - 데이터 최소 수집 원칙 정합. 이벤트 1회를 위해 영속 계정 만들 필요 없음.
  - 1순위 시장(학교 졸업식) = 미성년자. 미성년자 데이터의 영속 보유는 자산이 아니라 법적 부채.
  - 1년 1~2회 사용 빈도에서 월 단위 재방문 SaaS형 마케팅 모델은 한계 효용 작음. 영상 공유 자체가 더 큰 마케팅 채널.
  - 정찰에서 `organizerPhone`이 이미 이벤트별 저장 구조 확인 — 코드는 사실상 이벤트-바운드를 부분적으로 이미 구현 중. 계정 모델은 이걸 뒤집는 변경.
  - 비밀번호 제거 이유: 이벤트당 1회 사용에서 비번은 토큰 역할. 그러면 그냥 토큰을 쓰는 게 정직.
  - 탈퇴 모듈 불필요. 운영 부담 감소.
- **마케팅 데이터 자산화 의제 (보류)**: 향후 BM이 B2C 1회성 외 방향으로 이동 시 재평가. 마케팅 동의는 별도 약관 항목으로 받을 수 있으므로 이벤트-바운드 모델에서도 동의 기반 마케팅 가능.
- **Firebase Auth 처리**: 끊지 않고 그대로 둠. 사용 안 함. 향후 되돌리기 옵션 보존.
- **대안**: 계정 모델(가입/로그인 분리, hosts 컬렉션 신설) — 위 이유들로 기각.
- **2026-05-19 정정**: 본 결정은 2026-05-19 결정으로 **폐기**. 계정 모델로 회귀. 이유는 영업 개시 후 결제·마이페이지·다회 사용 지원 정합.

## 2026-05-09 — 호스트 인증: 가입/로그인 페이지 분리, 1차안에서 인증 절차 최소

- **결정**: 호스트 인증을 가입 페이지 + 로그인 페이지 분리 구조로 정비. 가입 입력 필드: 이메일, 비밀번호, 휴대폰번호, 이용약관 동의.
- **이유**:
  - 정찰에서 가입 흐름이 코드에 없음을 확인 (signup 함수 없음, 운영자 계정은 Firebase 콘솔 직접 생성). 신규 이메일로 로그인 시 "비번 또는 이메일이 올바르지 않음" 에러로 막다른 길 → 두 번째 호스트 검증 자체가 불가능.
  - 1차안에서 이메일 인증·SMS 인증·자체 비번 찾기는 제외. Firebase Auth 기본 `sendPasswordResetEmail`은 그대로 유지.
- **대안**:
  - 신규/재방문 분기 (한 화면에서 이메일 입력 후 분기): 이메일 enumeration 보안 이슈 + 분기 API·UI 상태 관리 추가 비용 → 기각.
  - 가입 시 이메일·SMS 인증 즉시 도입: 발송 비용 + 도달성 의제(known-issues 네이버 메일) 미해결 상태에서 마찰만 늘림 → 1차안 제외.
- **2026-05-19 정정**: 본 결정이 2026-05-19 결정으로 부활됨 (가입 페이지 신설). 다만 사양 일부 정정 — 이메일 인증 발송 포함, 가입 페이지 경로 `/signup`, 가입 입력에 이름 추가, 약관 + 개인정보 동의 분리 체크박스.
